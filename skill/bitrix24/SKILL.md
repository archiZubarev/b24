# Битрикс24: REST, вебхуки и ключи

Скилл держит две вещи: как безопасно получить доступ к порталу и как по нему
работать. Доступ — это утилита `b24`: ключи лежат в Связке ключей (macOS) или
в Диспетчере учётных данных (Windows), а ты вызываешь портал через MCP-сервер
`b24` или команду `b24 call`, не видя самих ключей. Документация методов —
MCP-сервер `b24-dev-mcp` (официальный, только справка, к порталу не ходит).

## Ключ — это пароль

Ссылка входящего вебхука `https://портал/rest/ID/токен/` даёт всё, что
разрешено вебхуку, от имени его владельца, без логина и без двухфакторной
проверки. Отсюда правила, которые держат ключ вне переписки:

- Никогда не проси вставить ссылку вебхука в чат. Ключ человек добавляет сам
  в терминале: `b24 add <имя>` (ввод скрыт) или `b24 add <имя> --clipboard`.
- Если ссылку всё же прислали в чат — не повторяй её в ответе и скажи, что
  после работы вебхук лучше пересоздать: чат хранится, ссылка из него уже не
  секрет. Сохранить её можно двумя способами, предложи первый:
  1. человек сам запускает в терминале `b24 add <имя>` и вставляет ссылку
     (скрытый ввод работает только у него — у тебя терминала нет);
  2. если человек просит сделать это тебе — передай ссылку на вход:
     `printf '%s\n' '<ссылка>' | b24 add <имя>` (вне терминала `b24 add`
     читает ссылку из stdin). Предупреди, что так она ещё раз попадёт в
     журнал вызовов инструментов.
- Не читай файлы с ключами (`cat ~/.что-то_webhook`), не выводи переменные
  окружения с ними, не запускай `b24 copy` — эта команда для человека и вне
  терминала откажет. Старые файлы переносятся без чтения: `b24 import`.
- В коде, тестах, заметках и коммитах — только имя ключа, не ссылка.

## Персональные данные

Право `user` отдаёт телефоны, почты, дни рождения сотрудников, `crm` —
контакты клиентов, `im` — переписку. Это персональные данные, и обращаться с
ними надо не мягче, чем с ключом: телефоны, почты, паспорта и прочие документы
людей не переносить в заметки, коммиты и ответ без нужды — для задачи обычно
хватает ID и имени. Выгрузки, где такие поля есть, сохранять в файлы вне
репозиториев и папок, которые синхронизируются с чужими, и в `select` брать
только нужные поля.

## Первый запуск

Начни с `b24 status` (или проверь, есть ли инструменты `mcp__b24__*`).
Что делать по ответу:

| Что видно | Что делать |
|---|---|
| команды `b24` нет | установить — [references/setup.md](references/setup.md), раздел «Установка» |
| `mcp b24` / `b24-dev-mcp` не подключён | `b24 setup`, затем перезапуск Claude |
| ключей нет | провести человека по созданию вебхука и выбору прав — setup.md, «Ключ» |
| ключ есть, но `b24 check` с ошибкой | разобрать ошибку — [references/rest.md](references/rest.md), «Ошибки» |

После `b24 setup` новые MCP-серверы появятся только в новом разговоре. До
перезапуска работай через Bash: `b24 call …` — это тот же клиент.

## Как работать с порталом

1. **Какой портал.** `bitrix_keys` (или `b24 list`) — какие ключи есть, их
   порталы и права. Ключ по умолчанию помечен; если порталов несколько и из
   задачи неясно, какой нужен, спроси.
2. **Сверь метод с документацией**, если не уверен в имени, параметрах или
   регистре полей: `bitrix-search`, затем `bitrix-method-details` в
   `b24-dev-mcp`. У старых методов (`crm.deal.*`) поля ЗАГЛАВНЫЕ, у новых
   (`crm.item.*`) — camelCase; путать их — частая причина пустых ответов.
3. **Читай** через `bitrix_read` (один вызов), `bitrix_list_all` (все страницы)
   и `bitrix_batch` (до 50 методов чтения разом). Всегда ставь `select` с
   нужными полями: ответ меньше, быстрее и не съедает контекст.
4. **Меняй** только через `bitrix_write` и только после того, как человек
   согласился с конкретным изменением: что за сущность, какие ID, какие поля
   и значения, сколько записей. Для массовой правки сначала покажи выборку и
   число записей. Напомни, что на стадиях могут стоять роботы и триггеры: запись
   через REST может их запустить, а через REST их не видно (rest.md, «Потолок
   вебхука»).
5. **Не дёргай портал в цикле по одной записи** — бери пачками: `batch`,
   фильтр по массиву ID (до сотен ID в одном `filter`), `bitrix_list_all`.
   Лимит — около двух запросов в секунду на портал; клиент сам держит паузу и
   повторяет при `QUERY_LIMIT_EXCEEDED`.

6. **Отвечай итогом, а не ответом портала:** числа и вывод («в октябре 14
   сделок на 3,2 млн, из них 9 выиграны»), а не простыня JSON. Сырые данные —
   в файл, если человек их просит. Для отчёта хватает одной строки итога и,
   при нужде, короткой таблицы.

Сервер `b24` делит инструменты на чтение и запись по имени метода: `get`,
`list`, `fields` и родственные — чтение, всё незнакомое — запись. Если
`bitrix_read` отказал, метод что-то меняет — это не ошибка, а повод спросить
человека и вызвать `bitrix_write`.

## Через терминал

Когда MCP недоступен, пишешь скрипт или нужна выгрузка в файл:

```bash
b24 call crm.deal.get id=12
b24 call crm.deal.list 'filter[STAGE_ID]=WON' 'select[]=ID' 'select[]=TITLE' --all > deals.json
b24 call --key lab crm.item.list --json '{"entityTypeId":1036,"select":["id","title"]}' --all
```

Параметры со скобками — в кавычках: в zsh (терминал macOS) `select[]=ID` без
кавычек — шаблон файлов, и команда упадёт с `no matches found`. Полный список
команд и инструментов — [references/cli.md](references/cli.md).

Для программы или скрипта, которому нужен ключ, не вшивай ссылку и не клади её
в файл рядом с кодом: пусть скрипт вызывает `b24 call` (ключ остаётся в
хранилище), а если нужен прямой HTTP — человек сам решает, где хранить ключ.
