# REST Битрикс24: как не наступать на грабли

Собрано из работы с облачным порталом в 2026 году и документации. Где
написано «проверено» — видели вживую; «по документации» — не проверяли сами.

Содержание: вызов и ответ · сущности · фильтры · даты · страницы · пачки ·
лимиты · ошибки · потолок вебхука · запись и автоматизация.

## Вызов и ответ

Запрос — POST на `https://портал/rest/<ID>/<код>/<метод>.json` с телом JSON.
Ответ: `result`, у списков ещё `total` и `next`, и `time` — в нём
`date_start` (часы портала, с поясом) и `operating` (израсходованное
«операционное время», см. «Лимиты»).

Два поколения методов CRM:

- старые: `crm.deal.*`, `crm.lead.*`, `crm.contact.*`, `crm.company.*` — поля
  ЗАГЛАВНЫЕ (`STAGE_ID`, `ASSIGNED_BY_ID`, `UF_CRM_1700000000`);
- универсальные: `crm.item.*` с `entityTypeId` — поля camelCase (`stageId`,
  `assignedById`, `ufCrm50Number`), ответ списка в `result.items`. Смарт-процессы
  (СПА) — только через них.

Какие поля есть — метод `*.fields` (`crm.deal.fields`, `crm.item.fields`).
Пользовательские поля — `UF_CRM_…`; у СПА префикс `UF_CRM_<id типа>_`
(в camelCase `ufCrm<id>…`). Значения списков (enumeration) приходят ID, а не
текстом: расшифровка в `*.fields` → `items`.

## Сущности

| entityTypeId | Что |
|---|---|
| 1 | лид |
| 2 | сделка |
| 3 | контакт |
| 4 | компания |
| 7 | предложение |
| 31 | счёт (новый) |
| 128–191, 1030+ | смарт-процессы; список — `crm.type.list` |

Стадии сделки: `NEW`, `WON`, `LOSE` в общей воронке и `C<id воронки>:NEW` в
остальных; у СПА — `DT<entityTypeId>_<id воронки>:NEW`. Воронки сделок —
`crm.category.list` с `entityTypeId=2` (старый `crm.dealcategory.list`),
стадии — `crm.status.list` с фильтром `ENTITY_ID`.

Смотри на семантику, а не на код стадии: `STAGE_SEMANTIC_ID` (`stageSemanticId`)
— `P` в работе, `S` успех, `F` провал. Провальных стадий бывает несколько, коды в
каждой воронке свои, а семантика не ломается при переименовании.

## Фильтры

- Операторы — приставкой к полю: `=`, `!`, `>`, `>=`, `<`, `<=`, `%` (содержит),
  `@` (входит в список, у `crm.item.list`). У старых методов массив значений
  сам означает «любое из».
- «Поле заполнено»: `filter[!UF_CRM_X]=` (пустое значение с `!`). Проверено.
- Массив ID в одном фильтре: сотни ID проходят одним запросом (проверено 400 —
  0,8 с). Только POST/JSON — в строку запроса не влезет.
- Всегда `select` с нужными полями: `select[]=*` и `UF_*` тащат всё и медленнее.

## Даты и часовые пояса

Портал живёт в своём поясе (у российских порталов часто Москва), компьютер —
в своём. Проверено:

- Дата без времени в фильтре (`2026-10-01`) — полночь по поясу портала.
- Время без пояса (`2026-10-01T10:00:00`) портал понимает по своему поясу —
  при разнице с компьютером фильтр съезжает на эту разницу.
- Время с поясом (`2026-10-01T10:00:00+07:00`, RFC 3339) портал пересчитывает
  правильно. Пиши так всегда, когда важна точность.
- В ответах даты — с поясом портала: `2026-09-25T12:49:54+03:00`.

Для «что изменилось с прошлого раза» отметку бери из `time.date_start`
ответа (часы портала), а не из часов компьютера: если те спешат, правки
выпадут из окна. Плюс запас 10–15 минут назад.

Сравнение «на конец дня» — в поясе портала: 23:30 по Москве и 03:30 по
Новосибирску — разные даты.

## Страницы

- Страница — 50 строк, следующая — `start=<next>`; `total` — сколько всего.
- Подсчёт `total` стоит времени. `start=-1` отключает его: страница вдвое-втрое
  быстрее (проверено: 0,2 с против 0,5 с). Тогда листать «по ID»:
  `order[ID]=ASC`, `filter[>ID]=<последний ID>`.
- Глубокое смещение дорогое: страница со `start=15000` и полными полями — около
  2 с. Для тысяч строк — «по ID», а не смещением.
- Много страниц сразу — пачкой: `bitrix_list_all` / `b24 call --all` делают
  первую страницу и затем пачки по 50 страниц.
- Цепочка «по ID» внутри одной пачки: `filter[>ID]=$result[p0][49][ID]`.
  Ссылка на короткую страницу пустеет, и выдача начинается сначала —
  останавливайся на первой странице короче 50.
- Новые сущности приходят и на лету: строка может повториться на стыке
  страниц — убирай дубли по ID.

## Пачки (batch)

- До 50 команд за запрос; команда — строка `метод?параметры` в обозначениях
  строки запроса (`filter[ID][0]=1&select[0]=ID`).
- `halt=1` — остановиться на первой ошибке; `halt=0` — выполнить всё, ошибки
  будут в `result_error` по именам.
- Ссылки между командами: `$result[имя][поле]`, `$result[имя][0][ID]`.
- Пустые наборы портал отдаёт массивом `[]`, непустые — объектом: разбирать
  оба вида.
- Пачка — один запрос для лимита частоты, но каждая команда тратит
  операционное время.

## Лимиты

- Частота: около 2 запросов в секунду на портал с запасом на всплеск
  (по документации — «протекающее ведро» ~50 запросов; у старших тарифов
  больше). Превышение — `QUERY_LIMIT_EXCEEDED` (503). `b24` держит паузу ~0,35 с
  и повторяет сам.
- Операционное время: квота на метод за 10 минут (по документации порядка
  480 с). Превышение — `OPERATION_TIME_LIMIT`; израсходованное видно в
  `time.operating`. Лечится сужением выборки и паузой, а не повторами.
- Лимит общий на портал, не на ключ: чужие интеграции его тоже едят.

## Ошибки

| Код | Что значит | Что делать |
|---|---|---|
| `insufficient_scope` | у вебхука нет права | отметить право в настройках вебхука; ссылка не меняется |
| `INVALID_CREDENTIALS`, `NO_AUTH_FOUND` (401) | вебхук удалён, выключен, истёк, владелец уволен, ссылка обрезана | создать заново, `b24 add` |
| `WRONG_AUTH_TYPE` (403) | методу нужен контекст приложения | вебхуку недоступно никогда |
| `ACCESS_DENIED` «Application context required» | то же | то же |
| `ACCESS_DENIED`, `ACCESS_ERROR` | у владельца вебхука нет доступа к объекту (чужая сделка, чат без участия) | ключ другого человека или права в портале |
| `ERROR_METHOD_NOT_FOUND` | метода нет (опечатка, модуль, тариф) | `bitrix-search` |
| содержательная ошибка («Chat ID can't be empty») | метод доступен, не хватает параметров | так и проверяют, есть ли метод: вызвать без параметров |
| `QUERY_LIMIT_EXCEEDED` | слишком часто | пауза, пачки |
| `OPERATION_TIME_LIMIT` | исчерпано время метода | сузить выборку, подождать |

## Потолок вебхука

Права расширяют вебхук вширь, но не вглубь. Закрыто типом авторизации,
никакие галочки не откроют (проверено 11.09.2026):

- подписка на события `event.bind` — `WRONG_AUTH_TYPE`. События для вебхука —
  только исходящий вебхук (портал сам стучится на ваш адрес, нужен публичный
  URL). По документации у мессенджера есть опрос событий без адреса:
  `im.v2.Event.subscribe` / `im.v2.Event.get` (scope `im`) — с вебхуком не
  проверяли;
- свои роботы и действия `bizproc.robot.*`, `bizproc.activity.*`,
  триггеры `crm.automation.trigger.*` — «Application context required»;
- встройки интерфейса `placement.bind`, часть телефонии и чат-ботов.

Роботов на стадиях в REST нет вообще — ни у вебхука, ни у приложения.
Выгружаются они только «Переносом настроек CRM» (CRM → Настройки →
Отраслевые сценарии). Экспорт — как резервная копия, безопасен. Импорт
**заменяет** настройки целиком и по документации удаляет существующие лиды
и сделки — на рабочем портале не запускать.

Что вебхуку можно при нужных правах (проверено): элементы СПА
(`crm.item.*`), стадии (`crm.status.add/update`), настройки СПА
(`crm.type.update`), поля СПА (`userfieldconfig.*`, нужно `userfieldconfig` +
`crm`), история стадий, вид карточек (`crm.item.details.configuration.*`),
сотрудники и отделы, чаты (создать, писать, читать), запуск классических БП
(`bizproc.workflow.start`).

## Запись и автоматизация

- Перед записью скажи человеку, что изменится, и дождись согласия; массовую
  правку сначала покажи выборкой и числом записей.
- На стадиях могут стоять роботы и триггеры, а через REST их не видно.
  Триггер «Отследить изменение полей» переносит элемент в свою стадию при
  изменении заданных полей; срабатывает ли он на запись через REST, в
  документации не сказано — проверять на тестовой сделке и смотреть
  автоматизацию стадии глазами.
- Запись идёт от имени владельца вебхука: в истории сделки и уведомлениях
  будет он.
- `im.chat.user.add` добавляет человека в чат с сообщением «присоединился» — на
  сотнях сделок это спам менеджерам.
